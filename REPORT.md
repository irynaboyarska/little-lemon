### 01 GET — базовий

- Метод: GET
- URL: https://httpbin.org/get
- Статус: 200 OK
- Основні поля: args, headers, method, origin, url

### 02 GET — параметри й заголовки

**Пояснення:** Query parameters передаються в URL після символу `?` і у відповіді httpbin відображаються в об'єкті `args`. Заголовок `X-Lab-Topic: 10` передається окремо та відображається в об'єкті `headers`. GET-запит не потребує Multipart Form, оскільки параметри фільтрації та пошуку можна передати через URL, а тіло запиту в цій роботі залишається порожнім.

### 03 POST — URL-encoded form

**Пояснення:** ціна `135` у полі `form` є рядком, оскільки URL-encoded form передає значення полів як текст. Запит містив форму, а сервер повернув відповідь у форматі JSON. Це підтверджується структурою відповіді та її заголовком `Content-Type: application/json`. Формат запиту й формат відповіді можуть відрізнятися.

### 04 POST — Multipart Form

**Пояснення:** заголовок `Content-Type: multipart/form-data; boundary=...` вказує на формат тіла запиту. Параметр `boundary` визначає межі окремих частин форми та автоматично генерується Postman. Сервер `httpbin` повертає отримані поля у форматі JSON, тому `Content-Type` відповіді — `application/json`. Отже, формат передавання даних у запиті може відрізнятися від формату відповіді сервера.

Порівняно з URL-encoded form, Multipart Form передає дані окремими частинами. В обох випадках отримані поля `form` однакові, а ціна `"135"` є рядком. Відрізняється спосіб кодування тіла запиту.

### 05 POST — JSON

**Пояснення:** синтаксично коректний JSON означає, що дані відповідають правилам формату JSON: правильно записані ключі, значення, лапки та дужки. Проте це не гарантує відповідності бізнес-правилам API. Наприклад, ціна страви повинна бути числом, а не рядком, навіть якщо обидва варіанти є синтаксично правильним JSON. Сервер httpbin лише повертає отримані дані й не перевіряє такі бізнес-правила.

Для дослідження вкладених даних було перевірено поля `json.title`, `json.published.year` та `json.published.day`. Вкладені значення знаходяться через послідовний перехід між об'єктами JSON. JSONPath дозволяє звертатися до потрібних елементів відповіді без перегляду всього документа. Він змінює лише спосіб відображення відповіді в клієнті, не впливаючи на HTTP-запит або дані сервера.

### 06 PUT — оновлення об'єкта

У відповіді поле `method` містить значення `PUT`, а поле `json` повертає весь переданий об'єкт із назвою, категорією, ціною, доступністю та датою публікації. Значення полів збережені у відповідних типах: `price` — число, `available` — логічне значення, `published` — вкладений об'єкт.

**Пояснення:** метод PUT зазвичай використовується для повної заміни представлення ресурсу. У цьому завданні httpbin лише повертає отриманий запит у відповіді, тому фактичного оновлення або збереження страви не відбувається.

### 07 PATCH — часткове оновлення

У відповіді поле `method` містить значення `PATCH`, а поле `json` містить лише передане поле `price`.

**Пояснення:** метод PATCH призначений для часткової зміни ресурсу. На відміну від PUT, він передає не весь об'єкт, а лише ті поля, які потрібно змінити. У цьому випадку httpbin тільки відобразив отримане поле у відповіді та не змінив раніше надісланий об'єкт.

### 08 DELETE — видалення об'єкта

У відповіді поле `method` містить значення `DELETE`, поле `data` порожнє, а поле `json` має значення `null`. Це підтверджує, що тіло запиту не передавалося.

**Пояснення:** метод DELETE зазвичай використовується для видалення ресурсу. Для цього запиту тіло не потрібне, оскільки ресурс зазвичай визначається через URL. Проте httpbin є echo-сервісом, тому він лише показує отриманий запит і не видаляє жодних даних.

### 09. GET — статус 204

Було виконано GET-запит на адресу `https://httpbin.org/status/204`. Сервер повернув статус `204 No Content`. Це означає, що запит успішний, але відповідь не містить тіла. Такий статус використовується, коли серверу немає потреби повертати додаткові дані.

### 10. GET — статус 404

Було виконано GET-запит на адресу `https://httpbin.org/status/404`. Сервер повернув статус `404 Not Found`, який означає, що запитаний ресурс не знайдено. Це приклад відповіді на звернення до неіснуючого ресурсу.

### 11. GET — статус 500

Було виконано GET-запит на адресу `https://httpbin.org/status/500`. Сервер повернув статус `500 Internal Server Error`. Він означає, що під час обробки запиту на стороні сервера виникла внутрішня помилка.

### 12 GET — метод не дозволено

Було виконано GET-запит на адресу `https://httpbin.org/post`, хоча цей маршрут призначений для обробки POST-запитів. Сервер повернув статус `405 Method Not Allowed`.

**Пояснення:** статус 405 означає, що сервер розуміє запит, але вказаний HTTP-метод не дозволений для цього маршруту. У цьому випадку для `/post` потрібно використовувати POST, а не GET.

# Порівняння способів передавання даних

Для передавання даних про страву було перевірено три формати: URL-encoded form, Multipart Form і JSON.

| Критерій                     | URL-encoded form                    | Multipart Form                     | JSON               |
| ---------------------------- | ----------------------------------- | ---------------------------------- | ------------------ |
| Content-Type                 | `application/x-www-form-urlencoded` | `multipart/form-data` з boundary   | `application/json` |
| Де знайдено поля у відповіді | `form`                              | `form`                             | `json`             |
| Тип значення `price`         | Рядок `"135"`                       | Рядок `"135"`                      | Число `135`        |
| Вкладений об'єкт             | Не підтримується як структура JSON  | Не підтримується як структура JSON | Підтримується      |

**Висновок:** URL-encoded form підходить для передавання простих текстових полів у закодованому вигляді. Multipart Form передає дані окремими частинами та також може використовуватися для передавання файлів. JSON є зручнішим для складних структур даних, оскільки підтримує числа, логічні значення, масиви та вкладені об'єкти.

Жоден із трьох запитів не доводить збереження страви на сервері, оскільки httpbin є echo-сервісом: він лише повертає отримані дані у відповіді та не зберігає їх як записи меню.

### Проєктування HTTP-методів та адрес для меню

Для роботи з позицією меню з ID `16` запропоновано такі запити:

- `GET /menu-items/16` — отримання інформації про позицію меню.
- `POST /menu-items` — створення нової позиції меню.
- `PATCH /menu-items/16` — часткова зміна позиції, наприклад оновлення лише її ціни.
- `DELETE /menu-items/16` — видалення позиції меню.

Для часткового оновлення ціни через PATCH у тілі запиту можна передати JSON: `{ "price": 150 }`.
